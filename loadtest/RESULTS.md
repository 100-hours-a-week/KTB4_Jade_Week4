# JVM 워밍업 부하테스트 결과

측정일: 2026-08-03 ~ 2026-08-04

서버 기동 직후 초기 응답 지연이 발생하는지 확인하고, 원인이 JIT 컴파일 단계와
어떻게 연결되는지 측정한 기록이다. 1~9절은 로컬 측정, 10절은 운영 적용, 11절은
미확인 사항이다.

판단 과정과 시계열 그래프는 [노션 회고](https://app.notion.com/p/3b1c255d936b8011ba55d15caf9d91d9)에
있다. 이 문서는 수치와 재현 절차를 맡는다.

---

## 1. 측정 환경

| 항목 | 값 |
| --- | --- |
| app 컨테이너 | 1 core / 1 GB |
| mysql 컨테이너 | 1 core / 1 GB, InnoDB buffer pool 256M |
| JVM | `-Xms512m -Xmx512m -XX:+UseSerialGC -XX:ReservedCodeCacheSize=128m` |
| JIT 로그 | `-XX:+UnlockDiagnosticVMOptions -XX:+LogCompilation` |
| 호스트 | Docker Engine 29.6.2, VM 11 core / 7.75 GB |
| 데이터 | 게시글 10,000건 (`created_at` 1년 범위 분산) |
| 부하 도구 | Locust |
| 대상 API | `GET /api/articles?size=10` |

데이터를 1만 건으로 잡은 이유는 buffer pool 256M에 전부 상주시키기 위해서다.
데이터가 커지면 디스크 IO가 응답시간을 지배해 JIT 신호가 묻힌다.

### 운영 환경과의 차이

측정 환경은 운영을 흉내내려고 잡은 것이지만 실제로는 일치하지 않는다. 운영은
t3.micro(2 vCPU / 1 GiB, 버스터블) 한 대다.

| 항목 | 로컬 측정 | 운영 (t3.micro) |
| --- | --- | --- |
| CPU | app 1 core (mysql 별도 1 core) | 2 vCPU 공용, 버스터블 |
| 메모리 | app 1 GB + mysql 1 GB = 2 GB | 전체 1 GiB |
| JVM 힙 | `-Xms512m -Xmx512m` 고정 | 미지정 (기본값) |
| GC | `UseSerialGC` 명시 | 미지정 |
| 같이 도는 것 | app, mysql | nginx, certbot, frontend×2, app×2, mysql |

**메모리는 로컬이 오히려 넉넉하다.** 운영은 1 GiB를 여러 컨테이너가 나눠 쓰고
컨테이너별 메모리 제한도 없다. 특히 블루-그린 배포 중에는 구·신 JVM이 동시에 떠
있으므로 이 시점이 가장 빡빡하다. CPU는 코어 수가 2배지만 버스터블이라 크레딧이
부족하면 베이스라인으로 떨어진다.

즉 이 문서의 로컬 수치는 운영보다 CPU는 불리하고 메모리는 유리한 조건에서 나온
값이다. 운영에 그대로 이식할 수 없다.

## 2. 부하 강도 결정

VU를 올리며 1분씩 측정했다. CPU는 부하 진행 중(35초 시점)에 샘플링했다. VU 5는
샘플링 시점을 놓쳐 CPU 값을 남기지 못했다. 강도 결정은 VU 10과 20의 비교로 충분해
다시 재지 않았다.

| VU | app CPU | mysql CPU | p95 (0-30s) | p95 (30-60s) | error |
| --- | --- | --- | --- | --- | --- |
| 5 | (측정 실패) | (측정 실패) | 27 ms | 19 ms | 0% |
| 10 | 61.3% | 23.2% | 33 ms | 11 ms | 0% |
| 20 | **100.6%** | 62.3% | 360 ms | 11 ms | 0% |

VU 20에서 1코어가 완전히 포화된다. 포화 상태에서는 초기 지연이 워밍업 때문인지
CPU 경합 때문인지 구분할 수 없으므로 **VU 10**을 본 측정 강도로 정했다.

## 3. 워밍업 횟수별 응답시간 (기동 직후 30초 구간)

조건당 3회 반복. app 컨테이너를 매번 재생성해 JVM을 새로 띄웠다.

| 워밍업 | 회차 | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| 0회 | 1 | 12 ms | 130 ms | 270 ms | 430 ms |
| 0회 | 2 | 16 ms | 230 ms | 1100 ms | 1600 ms |
| 0회 | 3 | 11 ms | 72 ms | 220 ms | 630 ms |
| 0회 | **중앙값** | **12 ms** | **130 ms** | **270 ms** | **630 ms** |
| 250회 | 1 | 12 ms | 84 ms | 660 ms | 1100 ms |
| 250회 | 2 | 10 ms | 18 ms | 64 ms | 150 ms |
| 250회 | 3 | 11 ms | 28 ms | 92 ms | 340 ms |
| 250회 | **중앙값** | **11 ms** | **28 ms** | **92 ms** | **340 ms** |
| 1000회 | 단일 | 10 ms | 14 ms | 27 ms | 66 ms |
| (참고) 60s+ 안정 구간 | 중앙값 | 9 ms | 13 ms | 16 ms | 160 ms |

워밍업 비용: 250회 7초(순차) / 13초(동시성 10), 1000회 36초. 이 절의 워밍업은 부하
시나리오 안에서 수행한 것이라 부하 없이 재는 4·5·6절보다 길다(1000회 기준 36초 vs 26초).

**편차가 크다.** 0회 p99는 220~1100 ms, 250회 p99는 64~660 ms 범위로 흩어진다.
250회 1회차는 max 1100 ms로 0회 1·3회차보다 나빴다. 한 번만 측정했다면 반대
결론이 나올 수 있었다. 꼬리 지표를 제대로 비교하려면 조건당 7~10회는 필요하다.

방향성은 일관됐다. 어느 회차든 0-30s 구간이 60s+ 구간보다 느렸고, 워밍업 횟수를
늘릴수록 격차가 줄었다. p50은 조건과 무관하게 10~12 ms로 거의 변하지 않는다.

## 4. 워밍업 횟수별 컴파일 레벨

부하를 걸지 않고 워밍업만 수행한 뒤 로그를 수집했다. 앱 코드(`kakaotech.task4`)만
골라 센 값이다.

| 워밍업 | L1 | L2 | L3 | L4 (C2) | 전체 L4 |
| --- | --- | --- | --- | --- | --- |
| 0회 | 0 | 0 | 0 | **0** | 1,069 |
| 250회 | 27 | 1 | 29 | **0** | 1,371 |
| 1000회 | 39 | 11 | 23 | **0** | 1,731 |
| 5000회 | 42 | 57 | 48 | **5** | 3,065 |

- **0회일 때 앱 코드는 아예 컴파일되지 않는다.** 전부 인터프리터 실행이다
- **1000회를 때려도 앱 코드는 C2에 도달하지 못한다.** 그런데 이 시점에 초기 지연은
  이미 사라졌다. 개선을 만든 것은 앱 코드의 C1 승격과 프레임워크(Spring, Hibernate,
  Jackson, Tomcat) 코드의 C2 승격이다
- **5000회에서 앱 코드가 처음 C2에 도달했다.** 5개 중 3개가 스트림 람다다. 요청 1회당
  서비스 메서드는 1회, 게시글 10건을 순회하는 람다는 10회 호출되므로 임계치를 먼저 넘는다

## 5. L2 급증의 원인 — C2 처리량 부족

L2는 C1으로 컴파일하되 프로파일링 정보를 수집하지 않는 단계다. JVM은 C2 큐가 밀리면
L3 대신 L2로 내린다. 워밍업 횟수를 늘릴수록 L2가 급증한 것이 이 신호로 보였다.

검증: **워밍업 1000회로 고정하고 컨테이너 CPU만 변경**했다.

| 항목 | CPU 1 | CPU 4 |
| --- | --- | --- |
| CICompilerCount | 2 | 3 |
| L1 | 1,300 | 1,344 |
| **L2** | **2,707 (34.1%)** | **32 (0.4%)** |
| L3 | 3,004 | 5,241 |
| L4 | 798 | 1,451 |
| **앱 코드 C2 도달** | **0개** | **5개** |
| 워밍업 소요 | 26초 | 11초 |
| 전체 컴파일 건수 | 7,931 | 8,187 |

전체 건수는 비슷한데 분포만 바뀌었다. 같은 메서드들이 1코어에서는 L2로 내려가고
4코어에서는 L3·L4로 올라간다.

**1코어 환경에서는 워밍업 횟수가 아니라 C2 컴파일 처리량이 병목이었다.** 1코어에서
5000회를 때려야 나오던 결과가 4코어에서는 1000회로 나온다. 워밍업 시간도 26초에서
11초로 줄었다.

## 6. 워밍업 엔드포인트 구현과 측정

배포 시 트래픽을 넘기기 전에 호출할 내부 엔드포인트를 만들었다.

```
POST /api/internal/warmup?count=1000
헤더: X-Warmup-Secret
```

앱이 자기 자신에게 실제 HTTP 요청을 반복한다. 서비스 메서드를 직접 호출하지 않는
이유는 필터 체인과 직렬화까지 같은 경로로 데워야 하기 때문이다. JIT은 실행된
메서드만 컴파일하므로 경로가 다르면 데워지지 않는다.

토큰은 앱이 내부에서 발급한다. 기존 회원 하나를 골라 `AccessTokenProvider`로 직접
만들기 때문에 배포 스크립트가 계정 정보를 알 필요가 없다. 회원이 없으면(첫 배포)
경고를 남기고 인증 없이 진행해 배포를 막지 않는다.

보호는 두 겹이다. 시크릿을 설정하지 않으면 엔드포인트가 404를 반환해 존재 자체를
드러내지 않고, nginx에서도 `/api/internal/`을 막는다.

| 호출 | 결과 |
| --- | --- |
| 시크릿 헤더 없음 | 404 |
| 시크릿 불일치 | 404 |
| 정상 | 200 + 결과 JSON |

### 엔드포인트 워밍업 1000회 (기동 직후 30초 구간)

| 회차 | p50 | p95 | p99 | max | 워밍업 소요 |
| --- | --- | --- | --- | --- | --- |
| 1 | 9 ms | 24 ms | 62 ms | 140 ms | 39초 |
| 2 | 9 ms | 16 ms | 59 ms | 110 ms | 35초 |
| 3 | 18 ms | 100 ms | 300 ms | 450 ms | 44초 |
| **중앙값** | **9 ms** | **24 ms** | **62 ms** | **140 ms** | |

1·2회차는 p50이 9 ms로 60s+ 안정 구간과 같다. 기동 직후와 3분 뒤가 구별되지 않는다.
3회차는 워밍업 자체가 44초로 느렸고 결과도 나빴다. 호스트 자원 경합으로 보이나 미확인이다.

### 외부 워밍업과의 차이

| 항목 | 외부 curl 1000회 (부하 없이) | 엔드포인트 1000회 (부하 없이) |
| --- | --- | --- |
| 전체 컴파일 건수 | 7,931 | 16,366 |
| L2 비율 | 34.1% | 30.2% |
| 앱 코드 C2 도달 | 0개 | 1개 |
| 소요 시간 | 26초 | 35~44초 |

엔드포인트 방식은 HTTP 클라이언트가 같은 JVM에서 돌기 때문에 클라이언트 코드까지
컴파일된다. 늘어난 컴파일 대부분은 실제 트래픽에서 쓰이지 않는 코드다. 1코어를
클라이언트와 나눠 쓰므로 소요 시간도 길어진다.

그럼에도 이 방식을 택한 이유는 대안들이 더 나쁘기 때문이다.

| 방식 | 계정 정보 | 불필요한 컴파일 | CPU 경합 |
| --- | --- | --- | --- |
| 외부 curl + 로그인 | **필요** | 없음 | 없음 |
| 앱 내부 엔드포인트 (채택) | 불필요 | 있음 | 있음 |
| 토큰만 발급 + 스크립트가 반복 | 불필요 | 없음 | 있음 |

외부 curl은 실계정의 이메일·비밀번호를 SSM 명령이나 CI 시크릿에 넣어야 한다.
배포마다 계정을 만들면 운영 DB에 쓰레기 계정이 쌓인다.

세 번째 방식은 컴파일 낭비만 없애고 CPU 경합은 그대로 남는다. 워밍업 대상과 횟수가
앱 설정과 배포 스크립트로 나뉘어 관리 지점이 늘어난다.

### 코드 캐시 확인

불필요한 컴파일이 코드 캐시를 압박하는지 확인했다. 엔드포인트 워밍업 1000회와
3분 부하를 모두 끝낸 뒤의 값이다.

```
CodeCache: size=131072Kb used=48016Kb free=83056Kb
total_blobs=16171, nmethods=15385, full_count=0
Compilation: enabled, stopped_count=0
```

128 MB 중 48 MB(37%)를 썼고 캐시가 찬 적은 없다. JIT이 멈춘 적도 없다.
클라이언트 코드까지 컴파일된 상태에서도 여유가 있어, 이 낭비는 실질적인 문제가
아니라고 판단했다.

## 7. 워밍업 대상 선정 실험 (조건당 7회)

목록만 데우면 상세 조회도 같이 빨라지는지 확인했다. 공통 경로(필터, JWT, Hibernate,
Jackson)를 공유하므로 목록만 데워도 충분하다면 워밍업 시간을 절반으로 줄일 수 있다.

| 조건 | 워밍업 | 소요 (평균) |
| --- | --- | --- |
| A | 없음 | — |
| B | 목록 500회 | 27초 |
| C | 목록 500회 + 상세 500회 | 45초 |

부하는 목록:상세 = 3:1로 섞었다(VU 10, 3분). 회차마다 app 컨테이너를 재생성해 JVM을
초기화했고, 실행 순서는 회차 단위로 무작위로 섞었다. 조건당 7회 반복했다.

본 측정 전에 조건당 3회를 먼저 돌렸으나 호스트에서 다른 작업을 하는 동안 측정해
오염됐다. 이 3회는 **예비 측정**으로 분리하고 본 집계에서 제외했다(7.2). 제외 기준은
결과값이 아니라 측정 환경이며, 값은 7.2에 그대로 남긴다. 원본은
`results/experiment/runs.jsonl`에 `phase: pilot`으로 보존돼 있다.

| 본 측정 7회 | **23 / 13 / 0.5** |

**흔들림이 조건이 아니라 시간대에 걸려 있다.** 예비 측정은 세 조건 모두 흩어졌고 본
측정은 세 조건 모두 안정적이다. 조건 차이가 원인이라면 특정 조건에서만 편차가 커야 한다.

예비 측정은 다른 작업과 같은 시간대에 연속 실행했고, 본 측정은 호스트를 비워 두고
돌렸다. 이 차이 말고 통제 조건은 동일하다. 다만 당시 호스트 부하를 기록해 두지
않아 **경합이 실제 원인인지는 미확인이다.**

예비 3회를 합쳐 10회로 집계해도 조건 간 순서는 바뀌지 않는다(목록 p95 중앙값
A 155 / B 28 / C 17 ms). 오염분은 편차만 키운다.

### 7.3 결론

**순서는 A > B > C(작을수록 좋음)로 뒤집히지 않았다.** 7회 전부 같은 순서다.

1. **워밍업은 효과가 있다.** 목록 p95 중앙값 A 160 → C 16 ms, 상세 150 → 10 ms
2. **목록만 데우면 상세가 덜 빨라진다.** 상세 p95 중앙값 B 14 vs C 10 ms, p99는
   87 vs 35 ms. 공통 경로만으로는 부족하고 고유 경로도 실행돼야 한다.
   `warmup.targets`에 상세를 넣는 게 맞다
3. **B의 불안정성이 남는다.** B는 목록 p95 표준편차 13(1회차 19 → 2회차 52), C는 0.5다.
   워밍업 대상에서 빠진 경로의 컴파일이 부하 시작 후로 밀리는 것과 일관된 방향이지만
   미확인이다
4. **예비 측정에서 나왔던 "B가 A보다 나쁘다"는 재현되지 않았다.** 본 측정 7회 전부
   B가 A보다 좋았다. 당시 관찰은 컴파일러 큐 적체가 아니라 예비 측정의 이상값
   때문이었다. 큐 적체 가설은 이 데이터로 지지되지 않으며, 별도 원인 분석 실험은 하지 않는다.
   5절에서 확인한 L2 급증과는 별개 사안이다. 여기서 기각하는 것은 "B의 미워밍업 경로
   컴파일이 부하 시작 후로 몰려 A보다 느려졌다"는 설명이다
5. C가 가장 좋은 것은 워밍업 대상이 부하 대상과 일치하기 때문이다. 이상 현상이 아니다

비용은 C가 45초로 B(27초)의 1.7배다. 배포 시간 18초를 상세 조회 p99 87 → 35 ms와
맞바꾸는 선택이다.

## 8. 기각한 가설

**커넥션 풀 미초기화** — 기동 직후 부하 0인 상태에서 MySQL 프로세스 목록을 확인한
결과 `loadtest` 커넥션 10개가 모두 Sleep 상태로 대기 중이었다. HikariCP는
`minimumIdle` 기본값이 `maximumPoolSize`라 기동 시점에 풀을 채운다.

**동시성 경로 미워밍업** — 워밍업을 동시성 1(순차)에서 10으로 바꿔 재측정했다.

동시성은 워밍업 요청을 한 번에 몇 개씩 보내는지다. `xargs -P` 값이 그대로 이 숫자다.

```
동시성 1  : [요청1]──[요청2]──[요청3]──...   서버 안에 항상 1건
동시성 10 : [요청1 ][요청11]...
            [요청2  ][요청12]...
            ... 10줄 동시 진행               서버 안에 항상 10건
```

가설은 이랬다. **JIT은 실제로 실행된 메서드만 컴파일한다.** 순차로만 데우면 톰캣 스레드가
하나씩만 돌고 커넥션도 하나씩만 빌린다. 그러면 커넥션 풀 대기나 락 경합처럼 여러 요청이
겹칠 때만 지나는 코드는 한 번도 실행되지 않는다. 실제 부하는 VU 10으로 동시에 들어오므로,
그 경로가 부하 시작 후에야 처음 컴파일되면서 초기 지연을 만드는 것 아닌가.

| 250회 워밍업 | p95 (0-30s) | max | 워밍업 소요 |
| --- | --- | --- | --- |
| 동시성 1 | 28 ms | 342 ms | 7초 |
| 동시성 10 | 28 ms | 190 ms | 13초 |

p95는 동일하고 max와 회차 간 분산만 개선됐다. 주된 원인은 아니다. 주범이었다면 p95도
같이 내려갔어야 한다. 다만 극단 꼬리는 실제로 줄었으므로 완전히 틀린 가설은 아니다.

**동시성을 올렸는데 워밍업이 더 오래 걸린 것**(7초 → 13초)은 app 컨테이너가 1코어이기
때문이다. 요청 10개가 동시에 도착해도 한 순간에 계산할 수 있는 건 하나뿐이라 나머지는
CPU를 기다리고, 스레드 전환 비용만 늘어난다. 게다가 그 CPU를 JIT 컴파일러 스레드도
같이 쓴다. 5절의 L2 급증(34.1%)이 이 경합의 결과다.

코어가 넉넉하면 반대가 된다. 운영에서는 같은 동시성 10으로 대상당 500회를 16.5초에
끝냈다(10.2).

## 9. 재현 방법

```bash
# 1. 서버 기동
docker compose -f docker-compose.loadtest.yml up -d --build mysql app

# 2. 시드 데이터 (기본 1만 건)
./loadtest/seed.sh

# 3. 부하테스트 — 워밍업 횟수를 인자로 준다
VUS=10 DURATION=3m ./loadtest/run-scenario.sh 0
VUS=10 DURATION=3m ./loadtest/run-scenario.sh 250

# 워밍업 엔드포인트를 쓰는 방식 (배포 스크립트가 실제로 쓸 방식)
VUS=10 DURATION=3m WARMUP_MODE=endpoint ./loadtest/run-scenario.sh 1000

# 코드 캐시 사용량 확인
docker compose -f docker-compose.loadtest.yml exec -T app jcmd 1 Compiler.codecache

# 웹 UI로 직접 조작하려면
docker compose -f docker-compose.loadtest.yml --profile locust up locust
# http://localhost:8089

# 4. JIT 컴파일 레벨 측정 (부하 없이 워밍업만)
./loadtest/jit-warmup.sh 1000 cpu1
./loadtest/jit-warmup.sh 1000 cpu4 docker-compose.cpu4.yml
python3 loadtest/analyze-jit.py loadtest/results/jit/*.log

# 5. 워밍업 대상 실험 (A/B/C를 회차마다 무작위 순서로)
./loadtest/warmup-target-experiment.sh 1 7     # 1~7회차
# 중간에 끊겼으면 남은 회차만 지정해 이어서 (조건:회차)
PLAN="C:5 B:5 B:6" ./loadtest/warmup-target-experiment.sh
python3 loadtest/analyze-experiment.py loadtest/results/experiment/runs.jsonl
```

결과물은 `loadtest/results/`에 쌓인다. 이 디렉터리는 gitignore 대상이다.

| 파일 | 내용 |
| --- | --- |
| `*_stats.csv` | 조건별 요약 통계 |
| `*_stats_history.csv` | 2초 간격 시계열 |
| `jit/jit-*.log` | JIT 컴파일 로그 원본 |
| `experiment/runs.jsonl` | 7절 실험의 회차별 원본 기록 (한 줄에 한 회차) |

`runs.jsonl`의 `phase`가 `pilot`인 3회는 오염된 예비 측정이라 집계에서 빠진다.
`analyze-experiment.py`가 `main`만 읽는다.

7절 예비 측정 3회는 `warmup-target-experiment.sh`가 생기기 전에 `run-scenario.sh`로 돌렸다.
파일 이름에 조건이 없어서 `backfill-rounds-1-3.py`가 당시 기록한 p95로 파일을 식별해
`runs.jsonl`에 복원했다. 재측정하지 않았다.

**이 스크립트는 이미 복원을 마쳤으므로 다시 실행할 일이 없다.** `runs.jsonl`이 존재하면
거부하도록 막아 뒀다. 굳이 다시 만들려면 기존 파일을 옮기고 실행한 뒤, 본 측정 21회를
다시 채워야 한다.

## 10. 운영 적용 (2026-08-04)

블루-그린 전환 전에 비활성 색상을 데우는 게이트를 배포 파이프라인에 넣었다.

```
docker compose up -d --wait <inactive>          비활성 색상 기동
docker compose exec <inactive> ... /auth/csrf   헬스체크
docker compose exec <inactive> ... /warmup      ← 추가
backend-upstream.conf 교체 + nginx -s reload    전환
```

워밍업 동안 활성 색상이 계속 서비스하므로 무중단이다. 컨테이너 하나를 제자리에서
교체하는 구조였다면 이 자리가 없다. 워밍업은 트래픽을 받지 않는 인스턴스가 존재할 때만
성립한다.

### 10.1 첫 배포 결과

```
{"requestedCount":500,"concurrency":10,"elapsedMs":16469,"authenticated":true,
 "targets":[{"path":"/articles?size=10","success":500,"failure":0,"elapsedMs":10111},
            {"path":"/articles/ak_88fd...","success":500,"failure":0,"elapsedMs":6286}]}

Backend blue-green deployment succeeded: active=blue tag=sha-2c879d6
```

1,000건 전부 성공했고 내부 토큰 발급도 정상이었다(`authenticated: true`).

### 10.2 배포 시간 비용

GitHub Actions 로그의 SSM 단계 소요 시간이다. 워밍업 적용 전 배포가 그대로 대조군이 된다.

| 배포 | 워밍업 | SSM 단계 |
| --- | --- | --- |
| 7/31 | 없음 | 43초 |
| 7/31 | 없음 | 48초 |
| 8/04 | 없음 | 56초 |
| 8/04 | **있음** | **76초** |

**20~30초 늘었다.** 워밍업 자체는 16.5초고 나머지는 회차 편차다.

로컬에서 45초 걸리던 워밍업이 운영에서 16.5초로 줄었다. 로컬 app 컨테이너는 1코어로
묶어 뒀지만 운영은 t3.micro의 2 vCPU를 쓴다.

다만 **5절의 CPU 1 → 4 실험을 그대로 대입하면 안 된다.** 그 실험에서 개선을 만든 것은
CICompilerCount가 2에서 3으로 늘어난 것인데, 운영은 4코어가 아니라 2코어다. 측정된 두
지점(1코어 → 2, 4코어 → 3)을 보면 2코어에서도 컴파일러 스레드는 1코어와 같은 2개일
가능성이 높다. 그렇다면 단축의 원인은 컴파일러 자원 증가가 아니라 요청 처리 병렬성이
2배가 된 것과 도커로 조인 1코어보다 실제 CPU가 빠른 쪽이다. **운영 CICompilerCount는
확인하지 않았다**(11절).

### 10.3 설정

| 위치 | 값 |
| --- | --- |
| `app.env` (EC2) | `WARMUP_SECRET`, `WARMUP_COUNT=500` |
| `application.yml` | `targets: /articles?size=10`, `/articles/{articleUuid}` |
| 동시성 | 10 |

시크릿은 컨테이너 환경변수를 컨테이너 안에서 읽는다. 호스트로 꺼내지 않아 SSM 실행
로그에 남지 않는다. 미설정이면 엔드포인트가 404를 반환하고 배포는 경고만 남기고
진행된다. 설정 누락이 배포를 막지 않는다.

## 11. 미확인 사항

- **7절 예비 측정 3회의 오염 원인 미확인.** 호스트 자원 경합으로 추정할 뿐 당시 호스트
  부하를 기록해 두지 않았다. 앞으로는 회차마다 호스트 load average도 남겨야 한다
- **7절 B의 회차 간 편차가 C보다 큰 이유 미확인.** 목록 p95 표준편차 B 13 vs C 0.5
- **3·6절은 여전히 조건당 3회다. 3절의 1000회는 단일 회차다.** 워밍업 횟수별(3절),
  엔드포인트(6절) 측정은 7회로 다시 재지 않았다. 7절에서 확인된 편차 규모를 감안하면
  이 표들의 중앙값도 확정값이 아니다. 특히 1000회는 한 번만 돌렸으므로 이 조건의 수치는
  확정값으로 쓰면 안 된다
- **운영(t3.micro 2 vCPU)의 CICompilerCount 미확인.** 1코어 2 / 4코어 3이 측정값이라
  2코어는 2일 것으로 보이나 확인하지 않았다. 이 값이 2라면 컴파일러 자원 면에서 운영은
  로컬 1코어와 같은 조건이고, 5절의 "L2 비율부터 보고 컴파일러 자원을 의심하라"는 순서가
  운영에도 그대로 적용된다. 확인 방법:
  `docker compose exec app-blue java -XX:+PrintFlagsFinal -version | grep CICompilerCount`
- **배포 순간의 메모리 여유 미측정.** 운영은 1 GiB에 nginx·frontend×2·mysql이 상주하고,
  블루-그린 전환 중에는 JVM이 2개 뜬다. 워밍업은 그 시점에 JIT 컴파일과 코드 캐시 적재를
  몰아서 한다. 컨테이너 메모리 제한도 JVM 힙 상한도 설정돼 있지 않다. 첫 배포는 성공했으나
  여유가 얼마나 남는지는 재지 않았다
- **CPU 크레딧 잔량의 영향 미측정.** t3.micro는 버스터블이라 베이스라인을 넘는 사용은
  크레딧을 소모한다. 워밍업 16.5초는 CPU를 몰아 쓰는 구간이다. 이 측정은 크레딧이 충분한
  상태에서 나온 값이며, 고갈 시 워밍업 시간이 얼마나 늘어나는지는 모른다
- **1코어에서 CICompilerCount를 늘렸을 때의 응답시간 영향 미측정.** 컴파일러 스레드가
  애플리케이션 스레드와 CPU를 다투게 되므로 별도 확인이 필요하다
- **`-XX:TieredStopAtLevel=1` 대조군 미측정.** C2를 막았을 때 워밍업 효과가 사라지는지
  확인하면 인과가 확정된다
- **운영에서의 개선 폭 미측정.** 워밍업 없이 전환했을 때 사용자 응답이 얼마나 느렸는지는
  재지 못했다. 전환 직후 운영에 부하를 걸어야 하는데 실서비스라 하지 않았다. 배포 시간
  비용(10.2)은 실측이지만 이득 쪽은 로컬 수치를 근거로 삼고 있다
- **운영에서 500회가 최적인지 미확인.** 1코어 기준으로 정한 값을 그대로 옮겼다.
  16.5초로 여유가 있어 늘릴 수도, 배포를 앞당기려 줄일 수도 있다
- **데이터 1만 건은 가볍다.** 실제 운영 규모의 병목은 재현하지 못한다
- **모든 가상 사용자가 동일 계정을 사용한다.** JWT는 stateless라 동시성 처리에는 영향이
  없지만, 조회 결과가 같아 캐시 적중률이 실제보다 높게 나온다
